# Zappy — subject

The requirements this project is built against, kept here so the code can be
checked against them. Where the subject leaves a choice open, what we
decided is in the [README](../README.md#choices-the-subject-left-open).

## Objectives

You have to create Zappy, which is an entirely automatic game where some AIs
play amongst themselves. It is about creating families/teams, surviving by
eating food and collecting stones in order to level up. Each level has
different requirements for a ritual, which makes the adventure more and more
difficult for the AI players, which play on their own, without any help from
their creator. The game is over once six members of one family/team reach
the highest possible level (8).

## Game presentation

### The game parts

- **The server** contains the field, the resources, and manages the logic
  and timing of the game.
- **One or many clients** connect to the server and each will "pilot" one
  player. The players are spread over teams.
- **A graphic client** connects to the server and displays the field and
  what happens there.

### Geography

The game consists in managing an entire world and its population. That
world, "Minerth", is geographically made of plains; there won't be any
obstacles on it.

The world is spherical and the game board is represented as a map. So if a
player leaves the board from the right, he will enter again from the left.

### Resources

The place contains many resources that can be used for survival: look for
them and get them before other players do. There are stones and food that
you will need to survive and evolve.

The stones are of 6 different types:

- jade
- peridot
- amber
- amethyst
- garnet
- ammolite

These resources must be randomly generated by the server. Despite being
random, the generation must follow some logical rules, for example:

- You can't put all the stones in one square.
- You can't put more than one food per square.
- Only one stone of each type in a square. You can have up to 3 stones of
  different types in the same square.

These are just some examples. It's up to you to decide the rules, but be
prepared to explain them to the auditors.

### General rules

- Each player starts with 10 food and 0 stones.
- Each player starts on level 1.
- As you level up, your player's sight improves.
- You must eat to survive and not starve and die.
- You must collect stones to level up.
- To win the game you must have at least 6 players of your family/team at
  level 8.

### Player

The local is happy just looking for stones and feeding on the way, but don't
be fooled by him: he can get greedy and kick you out of his way!

- He meets, without issues, other people on the same location and sees as
  far as the eye can see.
- It is impossible to guess the Minerthian orientation when crossing him.
- The food that the Minerthian picks up is the only resource he needs to
  live.
- One food unit allows him to survive 126 time units, so 126/t seconds. The
  more he picks up, the more he lives.

### Evolution ritual

The goal for everyone is to reach the top of the Minerthian hierarchy.

The ritual that increases the Minerthian physical and mental capacities is
performed as follows. You need to gather on the same field unit (square):

- a specific set of stones;
- a specific number of players of the same level.

The player starts the enchantment and the evolution starts.

- It is not necessary that all the players are on the same team, but they
  need to have the same level.
- All players participating in the enchantment reach a higher level.
- Only one player starts the enchantment; the others go to him and join.
- Only after two or more players are on the same square can they start the
  enchantment.
- If one of the members dies, the others continue the enchantment, unless
  the player is left alone; if that happens he has to start the process of
  enchantment again.

Combinations of resources and players needed for the enchantment:

| Level | Players | jade | peridot | amber | amethyst | garnet | ammolite |
|---|---|---|---|---|---|---|---|
| 1 → 2 | 1 | 1 | 0 | 0 | 0 | 0 | 0 |
| 2 → 3 | 2 | 1 | 1 | 1 | 0 | 0 | 0 |
| 3 → 4 | 2 | 2 | 0 | 1 | 0 | 2 | 0 |
| 4 → 5 | 4 | 1 | 1 | 2 | 0 | 1 | 0 |
| 5 → 6 | 4 | 1 | 2 | 1 | 3 | 0 | 0 |
| 6 → 7 | 6 | 1 | 2 | 3 | 0 | 1 | 0 |
| 7 → 8 | 6 | 2 | 2 | 2 | 2 | 2 | 1 |

### Vision

The player's view of the field is limited. To improve it you have to level
up. With each evolution, the vision goes up one unit ahead, and one on
either side of the new line.

The first three levels (the player is on square 0):

```
              ---- ---- ----
             | 1  | 2  | 3  |
              ---- ---- ----
                  | 0  |
                   ----
                  Level 1

         ---- ---- ---- ---- ----
        | 4  |  5 |  6 |  7 |  8 |
         ---- ---- ---- ---- ----
             | 1  | 2  | 3  |
              ---- ---- ----
                  | 0  |
                   ----
                  Level 2

 ----- ----- ----- ----- ----- ----- -----
|  9  | 10  | 11  | 12  | 13  | 14  | 15  |
 ----- ----- ----- ----- ----- ----- -----
      |  4  |  5  |  6  |  7  |  8  |
       ----- ----- ----- ----- -----
             | 1  | 2  | 3  |
              ---- ---- ----
                  | 0  |
                   ----
                  Level 3
```

To know what's around him, the client sends the command `see` and the server
answers with the following string (for level 1):

```
{content-square-0, content-square-1, content-square-2, content-square-3}
```

The player cannot see himself. If there is more than one object on a square,
they are all listed, separated by a space:

```
              -------- -------- --------
             | amber  | garnet |        |
             | player | garnet |        |
              -------- -------- --------
                      |        |
                      |  food  |
                       --------
                        Level 1

{food, player amber, garnet garnet, }
```

### Time and game speed

The game speed is defined by a time unit. Each action in the game has a
duration proportional to this time unit.

- The time unit is defined by the function 1/t.
- t is passed as a parameter when the server starts.
- A time unit lasts 1/t seconds.
- The Minerthians use the second as the absolute time unit.
- An action executes in action/t seconds.

t is an integer. If t = 1, `advance` takes 7 seconds. By default t = 100, so
`advance` takes 7/100 seconds.

### Objects management

It is impossible to distinguish two objects of the same class; only the
class of an object can be identified. Two `amber` are the same, while
`garnet` is a different class from `amber`.

### Teams / families

The goal of the game is to create a team/family of six players and get them
to level 8.

At the beginning of the game your family only has one member, so you have
to perform the calling action to get more family members.

Each player starts with 10 food and is controlled by a client. The clients
cannot communicate or exchange data with each other outside of the game, in
any way.

### Calling

The `fork` command calls a ship: the player calls another member of his
family. Once the call is made, the player can carry on with his life while
waiting for the ship. When the ship arrives, a new player appears and
receives a random direction. This operation allows a new player to join.

`connect_nbr` sends back the number of connections underway and authorized
for this family, which also tells you how many free spots the family has.

- Time to call the ship: 48/t
- Time for the ship to arrive: 600/t

### Inventory

The `inventory` command shows what objects the player has and how much time
he has left. The server answers, for example:

```
{food 300, amber 4, garnet 7, ..., peridot 2}
```

### Kick

A player can kick all the players sharing his square. It pushes them in the
direction he is looking at. When a client sends `kick`, all the clients on
that square receive:

```
moving <K>\n
```

with K indicating the direction the player is looking to, which is where
the others are kicked. The kick only works on players: food and other
resources can't be kicked, and nobody can kick during the evolution ritual.

## Commands

The syntax must be exactly the following.

| Action | Command | Delay | Response |
|---|---|---|---|
| advance one square | `advance` | 7/t | `ok` |
| turn right 90 degrees | `right` | 7/t | `ok` |
| turn left 90 degrees | `left` | 7/t | `ok` |
| see | `see` | 7/t | `{square1, square2, ...}` |
| inventory | `inventory` | 1/t | `{garnet n, amber n, ...}` |
| pick an object | `pick <object>` | 7/t | `ok` / `ko` |
| drop an object | `drop <object>` | 7/t | `ok` / `ko` |
| kick the players off the square | `kick` | 7/t | `ok` / `ko` |
| broadcast | `broadcast <text>` | 7/t | `ok` |
| begin the enchantment | `enchantment` | 300/t | `evolution in progress`, then `current level : K` |
| fork a player | `fork` | 48/t | `ok` |
| number of unused connections of the team | `connect_nbr` | 0/t | value |
| death of a player | – | – | `death` |

All commands are strings ending with a newline. For any unknown or incorrect
command, the server must answer `ko`.

### Broadcast

To send a message, the client sends:

```
broadcast <text>
```

The server sends this line to all its clients:

```
message <K>,<text>
```

with K indicating the direction the sound comes from.

### Sound transmission

All players hear the broadcasts without knowing who sent them; they only
understand the direction the sound comes from, and the message.

The direction is given by the square through which the sound reaches the
player. Square `1` is the one in front of the player, and the squares around
him are numbered counter-clockwise from there. Sound is a wave that travels
in a straight line and the world is round, so the shortest path between the
emitter and the listener is chosen.

For example, a player A sends a broadcast that leaves through his square 4,
and player B receives it through his square 2.

If the broadcast is sent from the listener's own square, he receives it from
square `0`.

## The server

The server is the main engine between the AIs and the GUI. It exchanges all
data with the AIs and executes their instructions, and at the same time
sends the information to the GUI. It can be written in C, C++ or Rust.

It is a TCP server connecting the clients and managing the whole world. It
does not need to be hosted: the game runs on one machine, localhost is
enough.

### Server instructions

- Generate all the resources randomly, following the rules in the resources
  section.
- A request must never hang forever. The server must never block, and a
  client can be bounced if necessary.
- Execute the client requests in the order they are received.
- Requests are buffered, and the execution time of a command only blocks the
  player concerned.
- Using any `exec` function to run another server is forbidden.
- The server must stay available at all costs.
- Use connection multiplexing.

```
$ ./server
Usage: ./server -p <port> -x <width> -y <height> -n <team> [<team>] [<team>] ... -c <nb> [-t <t>]
    -p  is the port number
    -x  is the width of the world
    -y  is the height of the world
    -n  is the name of the teams
    -c  is the number of authorized clients per team
    -t  is the time unit divider (the greater t is, the faster the game will go)
```

Tip: a non-blocking architecture with a circular buffer for every player's
actions lets the data be stored while the actions are performed. The
approach is up to you.

## The client

The client can be written in any language.

```
$ ./client
Usage: ./client -n <team> -p <port> [-h <hostname>]
  -n is the name of the team
  -p is the port number
  -h is the name of the host, the default is localhost
```

The client is autonomous: it sends its commands to the server without any
human intervention.

### Client / server communication

Client and server communicate over TCP sockets. The port is given in the
programs' parameters.

The client sends its requests without waiting for them to be executed, and
the server sends back a message confirming each successful execution.

The client opens a socket on the server's port, and the connection goes as
follows:

```
server  WELCOME\n
client  team-name\n
server  nb-client\n
server  x y\n
```

`nb-client` is the number of clients the server can still accept for the
team `team-name`. `x` and `y` are the world's dimensions.

If the team name sent by the client doesn't exist, the server must print
`Error: the team <name of team> doesn't exist`.

The client can send up to 10 requests in a row without a response from the
server. Beyond 10, the server no longer takes them into account.

There is no chat room or sharing of data between players. A player can
still broadcast a message through a command sent to the server, which is
broadcast to all players (see sound transmission).

## Graphic interface

The project needs a graphic visualization client, simple, clear and
ergonomic, that shows a real-time representation of the world as it is on
the server.

- Using any game engine is forbidden.
- The interface must be at least 2D, using icons to represent the world.
- The in-game items must be visible.
- Clicking a square must show its details, such as how many of each item it
  holds, in a floating window, tooltip or similar.
- Sounds must be visualized.

The graphic part can be written in any language (JavaScript, Python, C,
C++, PHP, Perl, …). It communicates over the network with the server to
retrieve the contents of the map, the teams, the inventories — everything
needed to see what is happening in the game.

## Bonus

- A flag for a log mode when running the server.
- A flag for the resource and food density (different levels, for example).
- A seed in the server and the client, so that specific scenarios can be
  reproduced.
